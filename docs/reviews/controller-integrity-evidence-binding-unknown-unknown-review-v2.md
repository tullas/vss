# Controller integrity evidence binding: unknown-unknown review v2

**Verdict: ACCEPT**
**Milestone:** `controller-integrity-evidence-binding` (#161/#162)
**Review basis:** Final adversarial review of the revised design against current controller behavior and the requested edge cases. This is design review only; no implementation or controller-state repair was performed. This review was prepared by the proposal author; Constitutional review was performed by a separate fresh-context reviewer.

## Explicit defect reproductions

**#161 — residue changes identity when made clean.** Current `_changed_paths` admits `.secrets.baseline` after the repository-governance validator succeeds, and `_change_identity` includes its mode and content. Stashing it to meet the rebind clean-worktree guard changes that identity, so the prior validation cannot be rebound. The design's one-path `.secrets.baseline` provenance record captures HEAD, index, and worktree state before identity calculation. It removes only the captured path from governed identity; it does not relax cleanliness. A later absent/stashed file leaves the governed identity stable, while an altered or partial restoration fails the recorded fingerprint checks. The current validator checks fixed scope but does not authenticate suppression entries, so the revised design additionally requires secret scanning to consume the bound base-HEAD baseline. The modified residue therefore cannot suppress a finding in governed content.

**#162 — conflict plus empty CI can move identity and expose stale L3.** Current `ingest_ci` classifies an empty check list as passed and calls the generic `checkpoint` writer with a new worktree identity. Projection/materialization can then update source binding while keeping prior validation evidence available for reuse. The design closes this through a typed API-only CI writer, forbids generic `ci_observed`, rejects empty or incomplete inventory, binds observations to the existing source identity without changing it, latches conflict, and requires validation identity equality during replay and reuse. The concrete unsafe sequence is rejected before it can clear conflict or make old L3 reusable.

## Falsification matrix

- **Capture timing and origin:** only the fixed `.secrets.baseline` candidate is captured in the initialization event before governed identity calculation; later-created paths and caller exclusions are rejected. This proves the controller's cutoff and exact state, not who authored pre-init content. The base-HEAD scanner baseline prevents captured suppressions from influencing validation.
- **Paths and filesystem state:** rename, deletion committed as governed change, chmod, same-content metadata/type substitution, symlink, special file, gitlink/submodule, nested repository, normalization/case alias, ignored or untracked candidate, and any second residue path fail closed. Exact path bytes and supported regular-file mode are required. Staged/worktree disagreement and multiple candidates are rejected.
- **Preservation:** an exact captured file may be absent while preserved externally; restoring it must match path/type/mode/content. Partial restoration, stash/pop conflict markers, or a changed baseline fails. Clean index does not excuse dirty worktree, and staged residue is checked against its captured index/worktree identities. The exact `.local/secrets/development.auto.tfvars.example` rule remains a separate existing exception.
- **Provenance attacks:** no caller-supplied registration API exists; only one literal path and the existing validator result are accepted. Registering a source/docs file or newly created residue is rejected. Provenance is append-only and part of identity/evidence binding. It proves controller-observed state at initialization, not historical human intent; this is a bounded local controller record, not authentication.
- **Concurrency and replay:** stale generation, concurrent writer, changed branch/base/HEAD, provenance, or worktree between validation and append rejects without evidence append. Replay consumes recorded provenance and validation bindings deterministically when local residue is absent. Histories lacking new provenance or full identity-bound validation keep historical projection but quarantine evidence until explicit append-only migration; history is not rewritten.
- **Validation and #160:** validation receipts bind governed identity, residue-provenance digest, exact evidence/profile/policy inputs, and subject HEAD; identity movement invalidates reuse except the single #160 manifest/blob/receipt proof that reconstructs the same governed identity. That exception preserves no CI for A, requires exact CI(B), and does not weaken its human gate, ancestry, artifact, or authority guards.
- **CI completeness and adversarial observations:** zero, partial, duplicate, unknown, wrong-SHA, wrong-workflow, wrong-run-attempt, cancelled, skipped, neutral, nonterminal, API-failure, or ambiguous observations cannot pass. A same-job-name workflow modification fails the exact baseline blob pin. Classification is downstream of failure only. Wrong-SHA or late CI after identity movement cannot bind because subject and generation must still match.
- **Event injection and authority:** caller JSON/classification and generic `ci_observed` are not success writers; projection requires an event subject and identity equal to the pre-existing binding. A schema-valid history fully rewritten and re-sealed by a local operator remains outside the stated tamper-evident, non-authenticated local-history trust boundary; the design makes no cryptographic-authentication claim. All authority remains constant false.

## Outcome and limits

The final design closes the identified material failure modes at the design level and defines negative tests for the listed filesystem, evidence, CI, replay, and concurrency cases. It preserves strict cleanliness and existing #160 compatibility while keeping the fix within the controller's current identity/evidence paths. No new material design gap remains for the requested scope. This ACCEPT is a design disposition only: the specified executable tests, implementation, and canonical validation are still outstanding and implementation remains unauthorized until the repository-native review receipts advance the milestone.
