# Controller integrity evidence binding: unknown-unknown review

**Verdict: REVISE**
**Milestone:** `controller-integrity-evidence-binding` (#161/#162)
**Review basis:** Adversarial review of the design checkpoint against current controller behavior, schemas, and synthetic tests. This is design review only; no implementation or controller state repair was performed.

## Defect reproductions

**#161 residue/clean-worktree sequence:** `_changed_paths` adds `.secrets.baseline` when the repository-governance validator passes. `_change_identity` then hashes the path, kind, mode, and bytes. Removing the edit to satisfy `rebind_committed_head`'s clean-worktree guard removes it from the snapshot and changes the identity; the ordinary rebind accepts only unchanged identity or its fixed controller-repair case. Thus the prior validation identity cannot be reproduced after the required cleanup. No controller-owned residue registration or pre-initialization inventory exists today.

**#162 conflict/empty-CI sequence:** `ingest_ci` considers an empty completed-check list successful. It calls the general `checkpoint(..., "ci_observed", ...)` writer with the current worktree `change_identity`. The projector and materializer treat generic events carrying `change_identity` as advancing the bound HEAD and identity. The prior validation event remains in projection, and `validate("canonical")` can reuse the prior L3 receipt based on its level/digest without verifying exact source identity. `checkpoint` also allows `ci_observed` as a generic event kind. This reproduces the reported synthetic route; it was not exercised against a real milestone.

## Material gaps

1. **Residue eligibility and origin proof are underspecified.** The design requires controller-owned provenance but does not name a closed eligible path set, a capture point that precedes validation, or a proof that the candidate predated governed work. Capturing arbitrary dirty files at `init` could classify a source change deliberately planted before initialization as residue. Limit the new mechanism to a closed controller-owned path policy (initially the reported `.secrets.baseline`, subject to its existing governance validator), snapshot it atomically in the initialization event before computing the governed identity, and reject every other path as excludable. Keep the existing exact `.local/secrets/development.auto.tfvars.example` exception separate and unchanged. Bind path bytes, type, mode, index/worktree state, and content digest. Staged/unstaged disagreement, rename, deletion, chmod, symlink/type substitution, partial restore, stash conflict, or a changed baseline must fail closed. The design also needs a deterministic rule for legacy milestones that have no such snapshot.

2. **The #160 equivalence exception is ambiguous.** The approved #160 recovery proves that removing only registered checkpoint additions from B's governed snapshot reconstructs A's bound identity, while the full committed HEAD changes. The new design says validation is exact-identity-bound and says not to weaken #160, but does not define whether that reconstruction is the explicit equivalence rule that permits retaining L3. Specify that #160 may preserve/reuse L3 only when its existing manifest, exact artifact blobs, and receipt proof reconstruct precisely A's governed identity at B; otherwise invalidate L3 and require fresh validation. Keep CI invalidation and exact-head CI(B) mandatory in either case. No other rebind may infer equivalence.

3. **CI completeness/source and event admission are not defined.** “Complete required-check set” has no authoritative inventory or version, and the design does not state how actual GitHub evidence is distinguished from caller JSON. Current `ci_refresh` queries a SHA but does not validate a closed required-check inventory; `ingest_ci` accepts a caller document; generic `checkpoint` can append `ci_observed`. Define a closed, versioned required-check inventory and require exact repository/commit SHA, run and attempt identity, workflow identity, unique check identities, terminal conclusions, and complete set equality. Empty, missing, duplicate, partial, cancelled, or API-ambiguous results must fail closed or remain pending; skipped/neutral checks cannot count as success unless the pinned policy explicitly admits that named result. Failure classification must be controller-derived and cannot make CI pass. Make the typed CI observer the sole write path and reject/ignore no generic `ci_observed` event as a source transition. Replay must require CI event subject HEAD and identity to equal the already-bound source; CI never changes either.

4. **Validation write-time TOCTOU and history migration need rules.** The design requires evidence identity equality but does not say that the evidence's embedded identity is checked against the repository identity both before running profiles and again under the append lock. A validation for A could finish while the worktree changes to B, then be appended with B's current identity unless the checkpoint revalidates the evidence binding. Add an exact evidence-to-identity comparison at validation completion and append, under expected-generation and repository-identity checks. Define versioned replay behavior for older receipts without a complete identity: preserve their historical projection deterministically, quarantine them from reuse, and require fresh validation for any current transition. Do not reinterpret or rewrite old history.

5. **Filesystem and concurrency adversaries need closed behavior.** Use exact Git path bytes and canonical UTF-8/POSIX path validation; reject normalization aliases, case-fold ambiguity, gitlinks/submodules, nested repositories, special files, and unsupported modes. Record enough provenance to distinguish HEAD/index/worktree state; preserving/removing the exact residue must not relax the clean-worktree guard for any other path. Verify external stash preservation against the recorded content/mode when available; stash-pop conflict remains dirty and cannot be resolved by treating conflict markers as the captured baseline. Under concurrent invocations, re-read branch, base, HEAD, worktree, provenance and generation while holding the event lock immediately before append; stale or changed inputs append nothing.

## Authority and compatibility checks

The proposed constant-false authority boundary is correct. The implementation must keep review/validation evidence distinct from CI evidence; must not let CI clear `CONFLICT`; and must preserve ordinary `CI_PENDING` rebind constraints. The #160 path remains limited to its registered artifact-only proof, direct descendant and current generation, unchanged branch/base, clean worktree, retained receipt evidence and `CI_PENDING` result. Historical projection must be versioned or otherwise deterministic; no old history is rewritten.

## Limits

This review proposes design clarifications only. I did not run a production/GitHub CI ingestion, alter source/controller code, change #160 history/state, or modify M11.P. Current all-false authority declarations remain in force.
