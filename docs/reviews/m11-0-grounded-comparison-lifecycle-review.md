# M11.0 grounded comparison lifecycle review

## Finding

M10 has an initial profile/first v3 candidate path and a bounded v2 profile
revision path, but no transition that can derive a second distinct candidate
after the initial candidate receives `USE`. The comparison package requires two
distinct admitted grounded candidates, while Runtime makes each request
create-once. The gap is real; Candidate A remains legacy exploratory evidence
and is not migrated or mutated.

## Constitutional review

Keep the transition in the existing grounded-generation domain. A candidate
variation is a sealed, human-scoped identity and ordinal, not a provider seed,
random value, prompt authority, or production decision. It preserves profile,
canon, option, scene, shot, frame, and all grounding overlays. Each derived
request remains independently approvable and reservable. The transition is
bounded to one derived comparison candidate per base candidate and does not
change Runtime, provider, promotion, or video authority.

## Unknown-unknown review

The principal negative-space risk is accidental fan-out through repeated
variation identities or mutation of a consumed request. The remediation must
reject duplicate identities in one derivation batch, cap the batch at one
derived comparison candidate, seal variation identity into the request and
candidate provenance, and fail closed before credentials, reservation, or
provider transport. Provider randomness and arbitrary visual prompt edits are
excluded.

## Decision

Implement one explicit deterministic comparison-candidate derivation transition
for v3 grounded admissions. Preserve the base profile and production binding;
make the variation identity/ordinal the only candidate-level difference and
include it in the provider projection as a non-visual comparison marker. Keep
the existing create-once artifact boundary and require a separate approval for
the derived request.
