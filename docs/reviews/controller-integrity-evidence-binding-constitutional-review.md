# Controller integrity evidence binding: independent review

**Verdict: REVISE**

## Scope and independence

Reviewed the design checkpoint for `controller-integrity-evidence-binding` (#161/#162), the repository-native milestone controller and record schema, relevant controller tests, and the coordination protocol. This review was performed in a fresh context, separate from the design author. The reviewer label is accountability metadata only; it is not an authentication or identity claim. No implementation, controller state/history, #160 recovery, or M11.P material was changed.

## Material findings

1. **Residue provenance is required but not yet operationally defined.** The design requires pre-existing residue to be captured in append-only replayable history before/at milestone initialization, with path, type, mode, content identity, and pre-existence evidence. It does not define the capture operation, the exact eligible path set, where provenance lives before a milestone history exists, or how initialization/replay proves it predates governed work. This matters because `_changed_paths` currently admits a governance-valid `.secrets.baseline` edit into `_change_identity` while separately rejecting most sensitive paths; broadening that exception into caller-selected exclusions would create an identity bypass. See design “Root-cause model” and “Formal scope” / acceptance criteria; [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:147) and [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:176).

2. **Validation binding and #160 preservation need one explicit equivalence rule.** The design correctly requires reusable L3 evidence to match the currently bound governed identity, yet #160 currently preserves validation across an `identity_rebound` while moving to a descendant commit whose full committed identity includes the registered artifacts. The existing recovery separately proves that excluding only the exact registered artifact paths leaves the old source identity unchanged. The design should state whether this proof defines semantic identity equivalence for reuse, or whether the preserved evidence is quarantined and fresh L3 is required. Otherwise “fail closed” legacy replay and “#160 unchanged” can lead to divergent projection/reuse behavior. See [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:962), [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:1063), and [test_milestone.py](/home/tullas/github/vss/tests/dev_milestone/test_milestone.py:743).

3. **CI admission lacks an identified authority for the complete required-check set and a closed write path.** The design requires non-empty, complete checks and rejects caller-classified success, but does not identify how “required” is determined or how an admitted check observation is tied to GitHub’s result rather than caller-supplied JSON. `ci_refresh` fetches GitHub check-runs, while `ingest_ci` accepts a caller document; generic `checkpoint(..., "ci_observed", ...)` can also append CI events. In replay, `ci_observed` currently drives state transitions, and `_materialized` accepts the event’s `change_identity` as a new source binding. Specify the authoritative check inventory/source and close all generic event-ingestion paths; tests should attempt both direct checkpoint injection and validly resealed event histories. See [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:943), [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:1619), [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:1555), and [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:1079).

4. **The recovery and compatibility rules need a more exact replay contract.** The design says malformed or ambiguous legacy validation binding fails closed and CI cannot clear `CONFLICT`, but does not enumerate which historical event forms remain admissible, how old histories without an explicit validation identity are handled, or how conflict is latched against later `ci_observed` events during projection. Current `_project` lets CI status change the state and `checkpoint` accepts `ci_observed` as a generic event type. Specify projection invariants and migration behavior so append-only replay cannot reinterpret old or resealed events as a source transition. The required all-false authority boundary is clearly stated and matches the existing schema’s constant-false authority fields; preserve it in each new event/contract. See [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:933), [milestone.py](/home/tullas/github/vss/src/vss_dev/milestone.py:1555), [dev-milestone-record-v1.schema.json](/home/tullas/github/vss/schemas/dev-milestone-record-v1.schema.json:13), and [agent-coordination.md](/home/tullas/github/vss/docs/agent-coordination.md:159).

## Limits

This is a design review, not implementation validation. I did not run tests or mutate the native milestone controller. The reviewed design file and a pre-existing unrelated untracked local secret-example file were present before this review; neither was changed.
